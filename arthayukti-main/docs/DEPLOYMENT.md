# Deployment

The API runs on Render and the frontend on Vercel. Neither needs a secret: the only settings are two web addresses.

| Part | Host | Config |
|---|---|---|
| API (FastAPI) | Render, free web service | [render.yaml](../render.yaml) |
| Frontend (React, Vite) | Vercel, free hobby plan | [frontend/vercel.json](../frontend/vercel.json) |

## Settings

| Where | Name | Value |
|---|---|---|
| Render (API) | `ALLOWED_ORIGINS` | The Vercel site address, such as `https://arthayukti.vercel.app`. No trailing slash. Several addresses can be separated by commas. |
| Render (API) | `ENVIRONMENT` | `production` (already in `render.yaml`). Anything other than `development` or `test` refuses to start without a strong `SECRET_KEY`. |
| Render (API) | `SECRET_KEY` | Generated by Render (`generateValue` in `render.yaml`). At least 32 random characters. Changing it signs everyone out. |
| Render (API) | `PYTHON_VERSION` | `3.12.10` (already in `render.yaml`) |
| Render (API) | `DATABASE_URL` | Optional but recommended: a managed PostgreSQL address. `postgres://` and `postgresql://` both work (the API uses the psycopg 3 driver). Left empty, the API uses SQLite, which Render's free plan erases on every restart. |
| Render (API) | `FRONTEND_BASE_URL` | The Vercel site address, used to build the link in password-reset e-mails. No trailing slash. |
| Render (API) | `MAIL_BACKEND`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_FROM` | Only if password reset by e-mail is wanted. `MAIL_BACKEND=smtp` plus the SMTP values. Without them, reset requests return 503 "not available yet". |
| Vercel (frontend) | `VITE_API_BASE_URL` | The Render API address, such as `https://arthayukti-api-y7ah.onrender.com` (the live service's address; check the Render dashboard for yours). No trailing slash. It is read when the site is built, so change it and redeploy. |

## Order of steps

1. Push the code to GitHub.
2. Render: create the API and note its address.
3. Vercel: create the site with `VITE_API_BASE_URL` set to the API address, and note its address.
4. Render: set `ALLOWED_ORIGINS` to the Vercel address and let it restart.
5. Check it: open `<api address>/api/v1/health`, then open the site and run the whole demo.

## Before a demo

Render's free web services stop after about 15 minutes with no visits, and the first request afterwards can take up to a minute. Open the site and the health address a few minutes before anyone uses it.

## If something is wrong

| What you see | Likely cause |
|---|---|
| "We could not reach the calculator" | `VITE_API_BASE_URL` is wrong or empty, or the API is still waking up. Fix it and redeploy the frontend. |
| Browser console shows a CORS error | `ALLOWED_ORIGINS` does not exactly match the site address (check `http` against `https`, and any trailing slash). |
| `/api/v1/samples` fails on the API | The API was installed without `pip install -e backend`, so it cannot find `contracts/samples`. |
| Blank page on Vercel | The Vercel project's Root Directory is not `frontend`. |

## Database

The schema is created only by Alembic migrations. Nothing creates tables when the app starts.

```bash
cd backend && alembic upgrade head
```

Render runs this before starting the server (see `startCommand` in `render.yaml`). The free plan's disk is not kept between restarts, so SQLite data there is temporary.

**An existing local `arthayukti.db` made before this change** was built by the old startup code and already has an `alembic_version` row for revision `ac496f5d4c54`. That is the same id as the real initial migration, which used to be empty. So `alembic upgrade head` on that file does nothing and the old layout stays: `password_resets.token` instead of `token_hash`, and a single global unique index on the idempotency key. Nothing here touches the file. To get the current schema locally, point `DATABASE_URL` at a new file (for example `sqlite:///./arthayukti_new.db`) and run `alembic upgrade head`, or move the old file aside first. Public calculation routes and the samples work either way. Sign-in, saved data and password reset need the new schema.

**PostgreSQL:** set `DATABASE_URL` and the same `alembic upgrade head` runs before the server starts. The migration has no SQLite-specific code, but it has only been run on SQLite so far. Try it on a scratch Postgres before relying on it.

## Local development account

No account exists by default. To create one for local work only, set `SEED_DEMO_USER=true` and a `DEMO_USER_PASSWORD` of at least 12 characters in `backend/.env` (with `ENVIRONMENT=development`), then run `python -m app.db.init_db`. The password comes from your `.env`, never from the code.

## Password reset link

The e-mail contains `FRONTEND_BASE_URL/#/reset-password?token=...`. The frontend's reset screen reads the token once and removes it from the address bar. The "Forgot your password?" link on the sign-in screen asks for the reset; the e-mail link then opens the reset screen.
